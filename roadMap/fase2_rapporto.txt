65TASS - FASE 2 (DIAGNOSTICA JSON): RAPPORTO
===========================================

Data: 2026-11-24. Base: 65tass dopo la Fase 1 (64tass trunk r3301 +
aggiunte di 65tass), versione "1.60.3243+".

SINTESI
-------
- Nuova opzione --error-json=<file> ("-" = standard output), con
  --error-json-append=<file> e --no-error-json. Spenta di default.
- L'output testuale non cambia: i 49 test di prima sono uguali, e il
  testo resta su stderr o nel file di -E.
- Il JSON contiene esattamente i messaggi del testo, anche con --no-error
  (che zittisce solo il testo).
- Campi richiesti dalla road map: file, riga, colonna, gravita', nome della
  diagnostica, messaggio; in piu' la riga sorgente, la catena degli include
  e le note.
- Suite: 57 test, tutti verdi (8 nuovi in test/src/json).


1. OPZIONI
----------
  65tass --error-json=errori.json a.asm         JSON in un file
  65tass --no-error --error-json=- a.asm        solo JSON, su stdout
  --error-json-append=<file>                    aggiunge un oggetto per run
  --no-error-json                               annulla un --error-json

  - Il file si apre all'inizio della stampa dei messaggi: se non si puo'
    aprire, l'errore fatale "can't write error file" compare nel testo
    (con la posizione sulla riga di comando). Se la scrittura fallisce
    (disco pieno, provato con /dev/full) c'e' un errore fatale su stderr.
    In tutti e due i casi il codice di uscita e' 1, cosi' una CI non
    prosegue senza il file. (-E invece, come in 64tass, non cambia il
    codice di uscita.)
  - Con -M il file JSON e' elencato fra i target, come il file di -E.
  - Con "-" il riepilogo finale non va su stdout (come per -o -), cosi'
    stdout contiene solo il JSON.


2. FORMATO
----------
  Un oggetto JSON, un messaggio per riga (facile da leggere e da
  confrontare con diff):

  {"program":"65tass","version":"1.60.3243+","format":1,"diagnostics":[
  {"severity":"warning","name":"-Wshadow","message":"shadow definition 'uno'","file":"a.asm","line":9,"column":1,"source":"uno     = 2","included_from":[],"notes":[{"severity":"note","name":null,"message":"original definition of 'uno' was here","file":"a.asm","line":7,"column":1,"source":"uno     = 1","included_from":[]}]},
  {"severity":"warning","name":"-Wleading-zeros","message":"leading zeros ignored","file":"a.asm","line":12,"column":13,"source":"        lda 0001","included_from":[],"notes":[]}
  ],"errors":0,"warnings":2}

  severity       "error", "warning", "fatal"; "note" nelle note.
                 Un avviso reso errore da -Werror= e' "error".
  name           il " [-W...]" alla fine del messaggio testuale, tolto dal
                 messaggio: "-Wshadow", "-Wleading-zeros"... null se il
                 messaggio non ha nome (quasi tutti gli errori, .warn,
                 .error, .cerror). 64tass da' un nome solo agli avvisi
                 opzionali: dare un nome a ogni errore vorrebbe dire
                 cambiare tutte le funzioni di error.c (da valutare con
                 l'LSP della Fase 9).
  message        testo del messaggio, senza il nome.
  file           nome come nel testo; "<command line>" per un argomento
                 della riga di comando (line = numero dell'argomento,
                 source = l'argomento); null senza posizione (es. "can't
                 open file" del sorgente principale).
  line, column   da 1. La colonna conta i caratteri, non i byte (una
                 tabulazione e' 1, "è" e' 1), cioe' e' la stessa del testo.
  source         riga sorgente; dentro una macro la riga espansa (quella
                 che il testo mostra sotto il messaggio).
  included_from  catena degli include dal file piu' vicino al principale:
                 [{"file","line","column"}...]. Il testo la stampa solo
                 la prima volta ("In file included from"); il JSON la da'
                 sempre per intero. L'espansione di una macro conta come
                 un include, come nel testo.
  notes          le note che il testo stampa dopo il messaggio.
  errors,        quanti messaggi di quel tipo ci sono nella lista.
  warnings
  format         1; cambia solo se un campo cambia significato.

  Come nel testo: con errori gli avvisi non compaiono, con -w nemmeno; i
  messaggi doppi sono gia' tolti. Le stringhe sono UTF-8 (il sorgente e'
  sempre convertito in UTF-8 da file.c) con gli escape JSON (\" \\ \t \n
  \r \u00xx); un byte non valido diventa �.

5. LIMITI E PROSSIMI PASSI
--------------------------
  - Nessun nome per gli errori (vedi name). Per l'LSP (Fase 9) potrebbe
    servire un codice stabile per ogni errore (Error_types).
  - Nessuna colonna finale: 65tass conosce solo il punto d'inizio.
  - VS Code: un "problem matcher" lavora gia' sul testo (file:riga:col:
    gravita': messaggio); il JSON serve a un'estensione o all'LSP della
    Fase 9, e alla CI (per esempio per le annotazioni di GitHub Actions).
  - Il 64tass originale non ha l'opzione: con --asm i test json/
    falliscono.
